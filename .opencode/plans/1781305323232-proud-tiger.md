# Plan: XBRL Definition Linkbase Anchoring (Custom→Standard Tag Mapping) — As Implemented

## Goal

Add the ability to fetch and parse XBRL **calculation linkbases** from per-filing EDGAR packages to extract custom→standard tag anchoring (e.g. `bac:FeesAndCommissions1` → `us-gaap:NoninterestIncome`). The implementation fetches per-filing XBRL exhibits on demand rather than relying on the companyfacts API.

## Current State (unchanged)

- **Companyfacts API** (`data.sec.gov/api/xbrl/companyfacts/CIK{cik}.json`): Returns flat observations with no linkbases, definition arcs, or anchoring metadata.
- **Filing index**: Fetched via HTML `-index.htm` page (parsed with regex). Discovers `EX-101.*` documents.
- **Filing documents**: Accessed via `Url::CikAccessionDocument(cik, accn, filename)` → `raw_request()` → `response.text()`.
- **XML parsing**: Uses `quick-xml` v0.39.2 (streaming event-based pull parser).

## Deviations from the Original Plan

### Deviation 1: Companyfacts API has no custom extension tags

**Assumption:** The companyfacts API contains filer-specific custom namespaces (like `aapl:MyCustomRevenue`) that could be detected and used to identify which filings have extension tags.

**Reality:** The companyfacts API only surfaces facts from recognised SEC/IFRS taxonomies (`us-gaap`, `dei`, `ffd`, `cef`, `ifrs-full`). **No filer-specific custom extension tags appear** — they live only inside per-filing XBRL packages on EDGAR. Verified across 100+ random tickers. This broke the original approach of using companyfacts for discovery.

**Resolution:** Changed the fetch function to directly scan periodic filings (10-K, 10-Q) from the CIK submissions API, fetching each filing's XBRL exhibits independently.

### Deviation 2: `-index.json` has no SEC document types

**Assumption:** The `CikAccessionIndexJson` URL (`{accn}-index.json`) would contain document entries with SEC document types like `"EX-101.DEF"`.

**Reality:** The JSON filing index (`.../index.json`) only contains MIME types (`"text.gif"`, `"image2.gif"`, `"compressed.gif"`). The SEC document type information (e.g. `"EX-101.DEF"`) is only available in the HTML `-index.htm` page.

**Resolution:** Reverted to the existing `fetch_filing_index` function which parses the HTML `-index.htm` with regex. Added `FilingIndex::definition_linkbase()`, `::calculation_linkbase()`, `::label_linkbase()`, etc. as filters. The `CikAccessionIndexJson` URL variant was kept for future use but is not used by the fetch function.

### Deviation 3: Definition linkbases lack polarity arcroles (the fundamental data-source pivot)

**Assumption:** The per-filing definition linkbase (`EX-101.DEF`) contains `general-special`, `essence-alias`, and `wider-narrower` definition arcs linking custom extension tags to standard GAAP concepts.

**Reality:** Across **every company checked** (AAPL, BAC, JPM, WMT, MSFT, GOOGL, AMZN, TSLA, XOM, IBM, GM, F, and more), the per-filing `EX-101.DEF` files contain **only dimensional arcroles**: `domain-member`, `all`, `hypercube-dimension`, `dimension-domain`, `dimension-default`. The polarity arcroles (`general-special`, `essence-alias`, `wider-narrower`) do not appear in per-filing linkbases — they exist only in the **standard US-GAAP taxonomy release** `-def-*.xml` files (which describe GAAP-internal hierarchy, not company-specific tags).

**Resolution:** Switched to the **calculation linkbase** (`EX-101.CAL`), which contains `summation-item` arcs. In a `summation-item` arc, the `from` concept is the parent/total (a standard GAAP concept) and the `to` concept is the child/detail (often a custom extension tag). This IS the polarity anchoring — the custom tag inherits its polarity from the standard parent it rolls up into.

### Deviation 4: Label linkbases use labelArc indirection

**Assumption:** The label linkbase directly maps locator labels to label text via matching `xlink:label` values.

**Reality:** The SEC's label linkbase uses a three-step indirection:
1. `<link:loc xlink:label="loc_bac_X" xlink:href="..."/>` → concept ID
2. `<link:label xlink:label="lab_bac_X" ...>Friendly Name</link:label>` → label text
3. `<link:labelArc xlink:from="loc_bac_X" xlink:to="lab_bac_X"/>` → connects loc to label

Loc labels and lab labels use different prefixes (`loc_` vs `lab_`), so the loc→label→text chain must be resolved via the labelArc elements.

**Resolution:** Rewrote `parse_label_linkbase` to parse `labelArc` elements and follow the indirection chain.

## Data Source (as implemented)

The actual anchoring source is the **calculation linkbase** (`EX-101.CAL`), not the definition linkbase:

```
https://www.sec.gov/Archives/edgar/data/{CIK}/{accn_unformatted}/
  - {company}-{date}_cal.xml   (calculation linkbase → summation-item arcs for polarity)
```

The calculation linkbase XML contains:
```xml
<link:calculationArc xlink:arcrole="http://www.xbrl.org/2003/arcrole/summation-item"
                     xlink:from="loc_us-gaap_NoninterestIncome"    ← standard total (polarity parent)
                     xlink:to="loc_bac_FeesAndCommissions1"       ← custom detail
                     weight="1.0"/>
```

**Note:** Not used by the fetch function — the JSON file only has MIME types, not SEC document types. Kept for future use.

### 2. Add XBRL-specific filters to `FilingDocument` / `FilingIndex`

- `FilingDocument::is_calculation_linkbase()` / `is_label_linkbase()` / `is_presentation_linkbase()`
- `FilingIndex::definition_linkbase()` / `extension_schema()` / `xbrl_instance()`

**File:** `src/models.rs` — registered.

### 4. Create definition linkbase parser (retained but unused by fetch)

**NEW file:** `src/parsers/parse_xbrl_definition_linkbase.rs`

Correctly parses `<link:loc>` and `<link:definitionArc>` elements. Includes `is_standard_namespace()` for standard taxonomy detection. **Not used by the current fetch function** because per-filing DEF files only have dimensional arcs. Retained for future use with standard taxonomy `-def-*.xml` files.

### 5. Create calculation linkbase parser (primary data source)

**NEW file:** `src/parsers/parse_xbrl_calculation_linkbase.rs`

Parses `EX-101.CAL` XML to extract `SummationItemArc` structs with `from`, `to`, `weight`, and `order`. Uses the same `ConceptRef` / `is_standard_namespace` machinery as the definition parser. Includes 3 unit tests.

### 6. Create label linkbase parser

**NEW file:** `src/parsers/parse_xbrl_label_linkbase.rs`

Parses `EX-101.LAB` XML. Follows the `labelArc` indirection chain: locator → labelArc → label text. Returns a `HashMap<String, String>` mapping concept IDs (e.g. `"bac_FeesAndCommissions1"`) to human-readable labels. Includes 3 unit tests.

### 7. Create extension schema parser (retained but not used in fetch)

**NEW file:** `src/parsers/parse_xbrl_extension_schema.rs`

Parses `EX-101.SCH` to extract `CustomElement` declarations with name, id, substitutionGroup, type, balance, and namespace prefix. Includes 2 unit tests.

### 8. Create fetch function

**NEW file:** `src/network/fetch_xbrl_anchoring.rs`

```rust
pub async fn fetch_custom_tag_anchoring(
    client: &SecClient,
    company_tickers: &[Ticker],
    ticker: &TickerSymbol,
) -> Result<DataFrame, Box<dyn Error>>
```

Algorithm:
1. Resolve ticker → CIK
2. Fetch CIK submissions, filter to recent periodic filings (10-K, 10-Q, 20-F)
3. For each filing:
   a. Fetch filing index HTML → find EX-101.CAL and EX-101.LAB documents
   b. Fetch and parse EX-101.CAL (calculation linkbase)
   c. Fetch and parse EX-101.LAB (label linkbase) for human-readable labels
   d. Filter to `summation-item` arcs where `from` is standard and `to` is custom
4. Build a DataFrame with columns: `ticker`, `cik`, `accn`, `filed`, `form`, `ext_concept`, `std_concept`, `label`
